# Analysis: the existing system at `10.181.1.5:1880`

Reverse-engineered from the live site on 2026-11-10. This document records **what is observed** and marks inferences clearly. It is the basis for the replacement design in [02-architecture.md](02-architecture.md).

## 1. What it is, in one paragraph

The site is a **Node-RED server** whose operator interface is a **FlowFuse Dashboard 2.0** single-page app at `/dashboard` (Vue 3 + Vuetify). The dashboard is called **"181Lyrix"** and is used to drive a church service: song lyrics, Bible passages, free text and images. The actual "screen" outputs are separate HTML pages (`/obs-main`, `/obs-mainfull`, `/obs-stage`) that OBS loads as Browser Sources. Those pages receive **raw JSON commands over WebSockets** (`/ws/obs-main`, `/ws/obs-stage`) and mutate their own DOM. All the business logic lives in the Node-RED flow, not in an application server or a database of its own.

There is a second, unrelated legacy dashboard at `/` (Node-RED Dashboard 1.0 / Angular) that controls the building: lighting scenes, DMX/audio racks, cameras, alarms. It is not part of the lyric workflow, but it shares the same Node-RED instance and shows what else is integrated (QLC+ lighting, X32 audio, OBS).

## 3. Operator UI

The dashboard has **7 pages, 14 groups, 46 widgets, 14 named users**. Navigation is a custom row of buttons injected into the app bar by a `ui-template` (`UI_Defaults`):

`Control` · `Entry` · `Songs` · `Song Editor` · `Misc` · 🌐 `Web` · ◀ · fade · ▶ · OBS transition

The nav buttons send messages with an explicit routing field, e.g.:

```js
send({ dest: 'UI',       payload: 'Control' })
send({ dest: 'lyrics',   topic: 'prev' })
send({ dest: 'lyrics',   topic: 'next' })
send({ dest: 'css',      topic: 'fade', payload: 'footer' })
send({ dest: 'obs-transition', topic: 'transition' })
```

So there are **two message dimensions**: `dest` (which subsystem: UI routing, lyrics, CSS, OBS transition) and `topic`/`action` (what to do). Node-RED routes on both.

### Control (`/control`)

- **Pages** table: numbered slides with `i`, lyric HTML, and component label (`c1`, `v1`, …). Clicking a row sends `{topic:'display', payload:{row}}`. The row of the currently displayed page is highlighted (`pageno`).
- **fade** button (`topic: fade`, `payload: footer`).
- **Quick Text** input (enter sends display text).
- **Preview** iframe loading `/obs-mainfull` — the operator sees the real output.
- **Set List (playlist)** table: `qid`, title, type icon (song / bulk / bible), transpose, delete, and drag-to-reorder. Clicking an item sends `{topic:'qload2', payload:qid}`. Moving uses `startMove` / `endMove`; deleting is a 3-step `startDelete` → `/` → `delete`.
- **Item notes** (`updateNote`), **Available Components** (`c1 v1 v2 v3 e1`), **Verse Order** (`verse_order`).
- **Max Lines per page** slider (`setMaxLines`), **Transpose for current item** slider.
- **QLC+/GM Now** and **QLC+/GM Fade** sliders on topic `/gm` — lighting desk integration (QLC+ = DMX lighting software; `/gm` = grand master).
- **Notices** image list showing relative paths; clicking sends `{topic:'qImage', payload: index}`.

### Entry (`/entry`)

- **Bulk** text area ("blank lines separate pages") with **Direct** (`topic:'direct'`, `{bulkdata}`) and **Setlist** (`topic:'addbulk'`, `{bulkdata}`).
- **Bible Text**: Translation dropdown, Book dropdown (66 books, 0–65), Chapter, From, To, and a chapter search table. Observed translations:

  `NIV2011`, `NIV-os`, `ESV`, `NASB`, `NET`

  The chapter index rows look like `{ id, title: "Genesis 1", bookname: "Genesis", chapter: 1, start }`. Selecting produces "Selected Bible Text" via a `ui-text`.

### Songs (`/songs`)

- Search table over the song library with `id`, title (with copyright, search title, first line `fta`, alternate title), type, source, edit, copy.
- Clicking a song sends `{topic:'addsong', payload:id}` (or an object in the other copy of the widget).
- At inspection time this table showed **"No data available"**, even though the Control page had a loaded song. The library appears to be populated on demand / from an external source and is not resilient.

### Song Editor (`/songEditor`)

- Same table shell; editor UI depends on selecting a song. Also empty at inspection. Intended actions `editsong`, `copysong`.

### Misc (`/misc`)

- **Body Font** dropdown (`body_font`) with ClearSans, Courgette, Handlee, Oxygen.
- **Playlists**: 16 saved playlists (e.g. `20-7-AM`, `2025-08-24`) with load/delete (`loadplaylist`, `deleteplaylist`). Playlists are persisted server-side.

### Web (`/web`)

- Four tabbed iframes, each fed by a URL text input (`S1`–`S4`). Observed:
  - ChurchSuite service plan 1 (AM): `https://oakhallchurch.churchsuite.com/plans/p7ep1exk`
  - ChurchSuite plan 2 (PM)
  - "Chords?" and "Other" pages.
- ChurchSuite is the external church-management/planning service. This page is effectively a browser-in-browser for planning, not presentation.

### OBS (`/tests`)

- An "OBS Controls" table, empty at inspection. Intended for OBS scene/transition control (`dest: 'obs-transition'`).

## 4. The display frontends

### HTML skeletons

- `/obs-main`: transparent-friendly page with `.header`, `.main`, `.footer` (footer text example: *"The Gospel call & The ultimate anchor"*), and `.footer-buffer`.
- `/obs-mainfull`: full-screen `.mainfull` + `.footer`.
- `/obs-stage`: `.main` arriving **pre-populated with a complete song including chord spans**, plus `.footer`; `body` has `background: black`, `font-size: 3.5vw`, 90% size.

All three load:

- jQuery **2.1.3** from `cdnjs.cloudflare.com`
- `/obs-main.js` and `/obs.css`
- Google Fonts (Courgette, Handlee, Indie Flower, Kalam, Oxygen) — an internet dependency at show time.

### Client script (`/obs-main.js`)

`connect()` picks the endpoint by pathname:

```js
loc.pathname.match(/obs-main/) ? '/ws/obs-main' : '/ws/obs-stage'
```

On close it retries every second. On message it `JSON.parse`s and interprets **commands that mutate the DOM by CSS class**:

```jsonc
{
  "innerHTML":    { "main": "<html>" },     // set innerHTML
  "textContent":  { "footer": "text" },     // set text
  "FinnerHTML":   { "main": "<html>" },     // fade out, set, fade in
  "FtextContent": { "footer": "text" },
  "visibility":   { "main": "hidden" },
  "display":      { "main": "none" },
  "misc": {
    "christmas": "selector",                // wrap every character in gold/blue spans
    "fadeOut": "selector",
    "fadeIn": "selector",
    "fioChristmas": "selector",
    "focus": "element-id",                  // scrollIntoView + .highlight
    "scrollIntoView": "element-id",
    "transpose": 2                          // semitones; rewrites .chord text
  },
  "css": "raw css appended to <head>"
}
```

For a key `k`, the selector used is effectively `k #k, .k` — i.e. **targets elements by class name**, not stable IDs. The script also supports transposition: `.chord` spans are rewritten with a 12-note table, slash chords are handled, and numeric `.tdiff` elements are shifted.

**Key consequence:** the output has no snapshot/state protocol. A newly opened or reconnected OBS source is blank until the operator sends the next command. `css` allows arbitrary CSS injection.

### Stage vs main

- The stage page contains chords and the full current song at page load, suggesting the Node-RED flow writes/generates the stage HTML (probably a `template` node), while the main pages are generic skeletons.
- `obs.css` hides `.chord` inside the Control dashboard table but the stage page displays them — stage is for musicians, main/mainfull for the congregation.

## 5. Runtime data model (from live dashboard messages)

### Lyric pages (Control "Pages" table)

```json
{
  "payload": [
    { "i": 1, "page": "Bless the <span class='chord'>C</span>Lord, …<br>…", "comp": "c1" },
    { "i": 2, "page": "The <span class='chord'>C</span>sun comes …",        "comp": "v1" }
  ],
  "pageno": 0
}
```

- A "page" is a chunk of lyric HTML, already split for display (max lines per page).
- Section labels: chorus `c1`, verse `v1`–`v3`, ending `e1`; an item exposes "Available Components".
- Chords are inline `<span class='chord'>C</span>` inside words, so the chord sits above the syllable in the stage view.
- Line breaks are `<br>`; stanzas are separate pages/rows.

### Set list

```json
{
  "CI": 3,
  "size": "40x2",
  "payload": [
    { "type": "bulk", "title": "(B) I believe in God the Father", "del": "X", "qid": 0, "transpose": 0, "move": -1 },
    { "type": "song", "title": "Your glorious cause OHK", "id": 0, "del": "X", "qid": 1,
      "transpose": 0, "style": "background: rgba(100,0,100,0.5)", "move": -1 },
    { "type": "song", "title": "Bless the Lord O my soul OHK", "id": 6, "del": "X", "qid": 2, … }
  ]
}
```

- `qid` = position in the set list; `CI` = current item.
- Item kinds observed: `song`, `bulk`, `bible`, plus images handled separately.
- Per-item `transpose` and `style`; per-item notes and verse order in the UI.
- Playlists are named and reused (dates, AM/PM).

### Song library rows

Columns: `id`, `fta` (title/first line field), `type`, `source.source`, `edit`, `copy`; content includes `title`, `copyright`, `search_title`, `alternate_title`, and HTML-rendered title. Formats are not visible from the UI, but the source field implies multiple imported sources — which matches the requirement for OpenLP XML, ChordPro and plain text.

### Bible

- Translation dropdown values: `NIV2011`, `NIV-os`, `ESV`, `NASB`, `NET`.
- Canonical 66-book list with numeric ids 0–65.
- Chapter index row: `{ id, title, bookname, chapter, start }`.
- Verse range selection uses **From** and **To** dropdowns (topics `start` / `end`), so a passage is chapter + verse range.
- The "Selected Bible Text" output is HTML.
- The user's stated plan — versions as **SQLite database files** — fits this model: one DB per translation, queried by book/chapter/verse.

### Notices / images

```json
{
  "files": ["Images/.dummy", "Images/qr-main.png", "Images/16 - Vox.png", "…"],
  "payload": [
    { "i": 0, "image": "Slides-1030-Pre/01 Its great to see you here!.png" },
    { "i": 1, "image": "Slides-1030-Pre/02 connect.png" }
  ]
}
```

- Directories observed: `Slides-1030-Pre/`, `Slides-1800-Pre/`, `Images/`.
- Names are relative paths; the image bytes are not served from the Node-RED root. Likely OBS reads local files or another server exposes them.
- Clicking a notice sends an index (`qImage`), not a path.

## 6. State, persistence and integration

- **Playlists are persisted** (16 visible) — likely as files in the Node-RED user directory or flow/global context.
- **Set list and current state are runtime state** held by the flow; the current display page is `pageno`/`CI` in messages.
- **Songs** appear to be loaded/pushed by the flow and were empty on the Songs page during inspection — a sign of coupling and fragile data loading.
- **Users**: the dashboard config lists 14 user ids; the FlowFuse socket has `withCredentials: true`, but the display pages and WebSockets are unauthenticated.
- **Integrations**:
  - OBS: display pages as Browser Sources + a transition command.
  - QLC+ / DMX lighting: `/gm` sliders and scene buttons (legacy dashboard).
  - Audio (X32), cameras, alarms: legacy dashboard.
  - ChurchSuite: iframe plan pages.
- **Message envelope** from the dashboard includes `_dashboard` (widget/template ids) and `_client` (socket id/ip), which Node-RED uses for per-client replies (e.g. dialogs).

## 7. Weaknesses of the current design

These are the concrete problems the replacement should fix:

1. **No authoritative state or snapshot.** Outputs only apply deltas; refresh/reconnect = blank or stale screen.
2. **DOM-by-class protocol.** Fragile selectors; any page structure change breaks output; arbitrary `innerHTML`/`css` injection.
3. **Two broadcast channels, no targeting.** All main outputs get every command; stage is a separate channel; no per-screen identity or acknowledgement.
4. **No authentication/authorization** on display pages or WebSockets; control UI relies on network isolation.
5. **Business logic inside Node-RED flows + inline Vue templates** with jQuery, Vue and Node-RED in one stack; hard to test, version or refactor.
6. **External CDN dependencies** (jQuery, Google Fonts) during services.
7. **Data source fragility** — the Songs page being empty while a song is live shows state is scattered.
8. **Images not served/managed by the app**; paths leak into messages.
9. **No import pipeline** visible for OpenLP, ChordPro or text; no schema/adapters.
10. **Presentation and planning mixed together** (ChurchSuite iframes inside the control app).

## 8. What we should keep

- The **operator workflow** and vocabulary: library → set list → pages → live output; quick text; Bible ranges; notices; per-item transpose; verse order.
- **Chords inline in lyrics**, hidden on the congregation output but visible on the stage output.
- **Page splitting** driven by "max lines per page".
- **Tiny, dependency-free output pages** — ideal for OBS Browser Sources; keep that property (but drop jQuery).
- **Transparent background + vw typography** so sources scale in OBS.
- **Multi-user control** with a preview iframe.
- **Separate HTTP frontends** per output role.
